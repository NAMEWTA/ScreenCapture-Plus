# 更新下载与文件边界

## 下载入口与用户控制

“设置 → 关于 → 下载最新版本”直接取得本仓库最新稳定 Release 的 Windows EXE。这个入口表示下载最新发行文件，即使当前运行版本已经是最新版，也可以再次下载。后台每日检查只在发现更高稳定版本、且应用空闲时提示，用户同意后进入同一下载流程。

下载完成后展示实际文件位置，并提供打开下载文件夹的操作。下载成功与程序已经更新是两个状态：下载不会自动执行新版、替换运行中的 EXE 或重启应用。用户需要先退出旧程序，将下载文件改成原程序的文件名（通常为 `huhucapture.exe`），再替换日常使用的 EXE 并重新启动；不应同时运行新旧两个副本。

## 系统目录与命名

下载目标通过 Windows 的 Downloads 已知文件夹取得。它跟随当前用户对“下载”目录的移动或重定向，不通过拼接用户主目录或写死磁盘路径推测位置。平台依据见微软 [SHGetKnownFolderPath 文档](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shgetknownfolderpath)。

完成文件使用 `huhucapture-<tag>-windows-x64.exe` 命名，例如 `huhucapture-v0.0.5-windows-x64.exe`。同名文件存在时排他创建带数字后缀的新文件，不覆盖用户原有下载。发行页的资产名称继续保持 `huhucapture.exe`，本地带版本的名称用于辨认各次下载。

下载目录与 Documents 中的媒体归档分别管理。剪切复制板的刷新、清空及媒体命名规则不影响下载的程序文件，更新下载也不改变截图和录屏归档位置。

## 何时可以报告成功

更新服务只选择本仓库稳定 Release 的指定 EXE；下载字节数、SHA256 和 EXE 版本必须与该 Release 的发布信息一致。界面不能把发现新版本或 HTTP 请求成功当成文件下载成功。

收到完整内容并通过长度、SHA256 校验后，才写入本次任务独有的 `.part` 文件，再核对 EXE 版本并提交为最终文件。只有最终文件已经落盘，才能展示成功及完整位置。保持成品与临时内容分离，异常终止留下的 `.part` 不能当成已完成下载或启动目标。

| 情况 | 必须保留的结果 |
| --- | --- |
| 网络中断、请求失败或发布信息不完整 | 明确失败，允许用户重试；不生成伪装成成品的 EXE |
| 下载长度、哈希或版本不匹配 | 拒绝提交本次文件，清理本次临时内容，保留已有下载 |
| Downloads 不可用、权限不足或磁盘写入失败 | 报告实际保存失败；不静默改存到应用目录或媒体归档目录 |
| 同名文件已存在 | 采用新的不冲突名称，保留原文件 |
| 关闭设置页或切换页面 | 回调不得访问已销毁控件；已完成的下载继续保留 |
| 应用退出 | 取消未完成请求，停止向已关闭界面发送结果；已完成文件保留，临时内容仅由其所属任务清理 |

## 扩展与验证

[更新服务](../src/services/Update.cpp)拥有检查、下载和完成状态，关于页面负责触发操作与展示结果。页面不应另外实现一套路径、HTTP、文件校验或覆盖规则。后台工作携带独立数据；语言、配置与 UI 更新仍在正确的线程和有效生命周期内执行。

下载验证应分别记录发行信息选择、真实文件提交和远端网络请求的证据。受控数据或本地测试可以证明校验与不覆盖规则，不能替代真实 Release 下载链路；未执行的网络、重定向目录和退出中断场景按 [验证指南](validation.md) 明确标注。
